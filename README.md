# tfm_environment

Benchmarks of the TFM kernels (Triton / TLX / Cutlass-CuTe / Gluon / Helion) on the
**hennessy** node (aarch64, NVIDIA GB10). Kernels are categorized into **compute-bound**
(`src/CBKernels/`, e.g., matmul) and **memory-bound** (`src/MBKernels/`, e.g., RMSNorm).
Everything is launched using a single executor: `ejecutar.sh`.

Thesis documents (tables, figures and written sections) are **not** in this repository: the
benchmarks write them to `../tfm/docs` (`~/hennessy/tfm/docs`; override with `TFM_DOCS`), and they
can be regenerated from `results/` without a GPU (`benchmarks/informe.py`, `resumen.py`,
`energia.py`, `productividad.py`).

### Tensor-core peak (`mma.sync` microbenchmark)

On sm_120/sm_121 every DSL ends up in `mma.sync` (there is no `wgmma`/`tcgen05`), so the real
ceiling is that instruction's throughput. `run_pico_mma` measures it directly: chains of
`mma.sync` on registers, with no memory access, sweeping warps per SM × independent
accumulators (`src/Microbench/`). Details and analysis in
`../tfm/docs/TFM/pico_mma.md`.

**NVIDIA GB10 (sm_121)**, job 20834, ~2.5 GHz:

| precision | peak | FLOP/cycle/SM |
|:---|---:|---:|
| TF32 | 61 TFLOP/s | 512 |
| FP16 / BF16 (f32 or f16 accumulate) | **122.7 TFLOP/s** | 1 024 |
| FP8 e4m3 / INT8 / MXFP8 | **243 TFLOP/s** | 2 048 |
| MXFP4 / NVFP4 (`kind::mxf4nvf4`, block-scaled, `sm_121a` only) | **487 TFLOP/s** | 4 096 |

- These are burst figures (~2.5 GHz). Pure MMA sustains 2.42 GHz (118.7 TFLOP/s FP16), but a
  real GEMM drops the clock to 2.08–2.18 GHz (`run_sostenido`, 6 s runs). The best kernels
  (cuBLAS, Triton+TMA, cuBLASLt FP8) sustain **75–77 %** of the nominal peak and **87–92 %** of
  the peak at their own clock: about half of the gap is clock, the other half is lost per cycle
  feeding the MMA.
- Saturating the MMA unit needs **≥ 8 warps per SM** (≥ 2 per sub-partition): one warp cannot
  issue more than one MMA every ~17 cycles.
- TMA raises per-cycle efficiency (92 % vs 85 % without TMA), but that kernel sustains a
  slightly lower clock, so the net gain is only +3.5 %.

The RTX 5090 (pascal) peak is pending (jobs 20838–20840).

`../tfm/docs/TFM/productividad.md`):

`<node>-frio` environment, which the performance summary ignores.

### Energy efficiency per DSL

With `TFM_ENERGIA=1`, every measurement also runs the kernel in a sustained regime (3 s idle,
then 6 s in a loop, the first 2 discarded) and records GPU power (NVML instantaneous), idle power,

`../tfm/docs/TFM/resultados/energia.md`). Results on GB10:

| Triton (block-ptr) | 1036 (×0.99) | — | — | — | — | — |
| Triton + TMA | **1064** (×1.01) | 1629 (×0.80) | — | — | — | — |
| Gluon | 861 (×0.82) | — | — | — | 6.37 (×1.07) | 6.37 (×1.06) |
| Helion | — | — | 875 (×1.03) | 425 (×0.50) | **6.50** (×1.09) | **6.47** (×1.07) |
| CUTLASS/CuTe | 573 (×0.55) | — | **930** (×1.10) | **900** (×1.06) | 6.00 (×1.01) | 4.68 (×0.78) |
| Reference | 1051 | **2037** | 847 | 851 | 5.95 | 6.02 |

GFLOP/J for compute-bound, GB/J for memory-bound; (×) = relative to the reference on the same GPU.
Shapes: matmul 8192³, attention B=4 H=32 N=4096 D=128, RMSNorm 16384×8192 (jobs 20849–20851).
GPU power is ~88–95 W in matmul and attention and ~38–49 W in RMSNorm (memory-bound kernels leave
the SMs idle). FP8 nearly doubles the work per joule at the same power; CuTe's matmul draws half the
power (43 W) but is the least efficient, because it leaves the GPU underused. Helion matmul failed in
autotuning (`helion.exc.NoTensorArgs`) and TLX does not run on GB10.

## Images (one per DSL)

Each DSL has its own Docker image, all defined as *targets* within the same `Dockerfile`
based on a common foundation (NGC PyTorch 25.10: torch, Triton, CUDA, and analysis tools).
The base image is built once and reused by all four.

| DSL | image | additions to base | kernels |
|:---|:---|:---|:---|
| Triton + TLX | `tfm-triton-tlx:ngc-arm64` | `triton-utlx` + `TRITON_PLUGIN_PATHS` | `src/*Kernels/triton/`, `triton_tlx/` |
| Gluon | `tfm-gluon:ngc-arm64` | none (Gluon comes with Triton; no TLX plugin) | `src/*Kernels/gluon/` |
| Helion | `tfm-helion:ngc-arm64` | Helion (`pip install -e`) | `src/*Kernels/helion/` |
| Cutlass/CuTe | `tfm-cutlass:ngc-arm64` | CUTLASS v4.8.0 in `/opt/cutlass` + CMake | `src/*Kernels/cutlass/` |

`ejecutar.sh validar <dsl>` verifies the baseline (PyTorch, Triton, tensor cores) and the DSL for that image on the GPU.
`exp` selects the image based on the benchmark folder (`benchmarks/<CB|MB>Kernels/<dsl>/`) or the `DSL=` variable.

## Execution

```bash
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar imagen                   # build + validate all 4 images
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar imagen helion            # just one
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar validar gluon            # validate only
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_matmul           # benchmark (triton-tlx image)
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp triton-tlx           # ALL benchmarks for a DSL
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp matmul               # one algorithm across ALL DSLs (each in its own image)
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp gluon rmsnorm        # one algorithm in one DSL
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_rmsnorm_gluon --dtypes bf16   # gluon image
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_matmul_fp8 --sizes 4096 8192
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_pico_mma         # tensor-core peak (mma.sync), ~2 min
bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_sostenido        # sustained clock-corrected peak vs matmul, ~3 min
TFM_CACHE_FRIA=1 TFM_MAQUINA=hennessy-frio bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp matmul --sizes 8192   # cold compile/autotune cost
TFM_ENERGIA=1 bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp matmul --sizes 8192   # energy efficiency (env <node>-energia)
DSL=helion bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp benchmarks/otro.py   # explicit image
VALIDAR=0 bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_matmul  # without prior validation
```

Within an interactive session (`~/srun_hennessy.sh`), without the queue:

```bash
~/tfm_entorno/ejecutar.sh exp plantilla --sizes 1024
~/tfm_entorno/ejecutar.sh shell cutlass   # bash inside the container of a DSL
```

- Environment: `<machine>` is the node, or use `TFM_MAQUINA=<name>` to isolate a different environment on the
same node (e.g., after changing the driver): `TFM_MAQUINA=hennessy-drv620 ./ejecutar.sh exp ...`. 
Results in the old format (`results/<benchmark>/`) are migrated with: `python3.11 benchmarks/migrar_resultados.py`.
- Log: `logs/<job-name>-<JOBID>.out`
- Results: `results/<machine>/<benchmark>/<date>_job<JOBID>/{resultados.csv,meta.json}` (where
`meta.json` stores the DSL, image ID, NVIDIA driver, and node kernel); `results/<machine>/<benchmark>/ultimo` points to
the most recent run, and `results/{matmul,rmsnorm}_metrics.csv` are regenerated using the
latest run for each benchmark.
- Every measurement also records the median SM clock and GPU power while it runs
(`reloj_mhz`, `potencia_w` columns, with a `triton_`/`cublas_` prefix in `run_matmul`; power is
NVML's instantaneous reading when available, see `potencia_fuente` in `meta.json`). Caveat: NVML
refreshes only every ~0.5 s and GB10 needs ~0.5 s under load to settle its clock, so a ~0.6 s
`do_bench` mostly sees the transient. For clock-corrected comparisons use `run_sostenido`
(6 s continuous runs, last 4 s counted).


## How it works

- Each execution uses an **ephemeral** container (`docker run --rm`) with this directory
mounted at `/workspace/tfm` (within the DSL image) and `PYTHONPATH=src:benchmarks` set;
there is no need to rebuild when changing code. Kernels are imported as packages:
`from CBKernels.triton.matmul import matmul`, `from MBKernels.triton.rmsnorm_baseline import rmsnorm`.
- `exp` warns if the GPU is busy and, by default, runs `benchmarks/validar_gpu.py` first.
- `src/Microbench/` holds hardware characterization code that is not a DSL kernel: the
`mma.sync` peak microbenchmark (`pico_mma_ext.cu`) is compiled with nvcc into a shared library
(`.cache/pico_mma/<hash>/`) and loaded with ctypes, so it can target `sm_121a`/`sm_120a`
(required by the block-scaled FP4/MXFP8 MMAs). It runs in the default triton-tlx image.

## Adding a kernel / benchmark

1. Kernel located at `src/<CB|MB>Kernels/<dsl>/<name>.py` (at the module level).
2. Benchmark: copy `benchmarks/plantilla.py` to
`benchmarks/<CB|MB>Kernels/<dsl>/run_<family>[_<variant>].py`. It is launched by its name,
and the **folder determines the image** (triton → triton-tlx, gluon, cutlass, helion). The name
must be unique across the entire `benchmarks/` directory (as it identifies the results):
e.g., `run_matmul_helion.py`. The prefix determines the consolidated table: `run_matmul_*` → `results/matmul_metrics.csv`,
`run_rmsnorm*` → `results/rmsnorm_metrics.csv`, `run_softmax*` → `results/softmax_metrics.csv`...
3. Validate the output against PyTorch using `benchmarks/validation.py`
(`comprobar_matmul`, `comprobar_rmsnorm`, `comprobar`, `error_rel`). 
**All matrix computations must use Tensor Cores** (`tl.dot`): call
`comun.exigir_tensor_cores(kernel_compilado)`, which aborts if the PTX lacks
`mma.sync`/`wgmma`/`tcgen05.mma`. Importing `comun` enables TF32 for fp32 in cuBLAS. 
Exception: operators without matrix multiplication (e.g., RMSNorm) do not use MMA and are measured in GB/s.
4. Measure using `comun.medir(fn, flops=..., bytes_movidos=...)` (returns ms, TFLOP/s, GB/s
and the SM clock / power sampled during the measurement via NVML) and finish with
`comun.guardar(filas, parametros=vars(args), resumen=...)`. To compare against the hardware,
use the `mma.sync` peak from `run_pico_mma` (`results/<machine>/run_pico_mma/ultimo/meta.json`,
key `resumen.pico`) scaled to the measured clock.
5. `bash ~/hennessy/tfm_entorno/ejecutar.sh encolar exp run_<...> [args]`.

## Reports for the thesis

**Summary by architecture** (`../tfm/docs/TFM/resultados/resumen_<arquitectura>.md` and
`resumen.md`): one table per GPU with DSLs in the rows and algorithms in the columns,
marked as CB (compute-bound, in TFLOP/s) or MB (memory-bound, in GB/s and % of peak).

**Per-benchmark tables** (`../tfm/docs/TFM/resultados/<machine>/<benchmark>.md` + `figuras/`) are
regenerated automatically after each run. To regenerate a run's report without a GPU: `python3.11 benchmarks/informe.py
results/<machine>/<benchmark>/ultimo` (or `--informe` for `run_pico_mma` / `run_sostenido`).

**Probes** (`.sonda/`) are throwaway diagnostics, indexed in [.sonda/README.md](.sonda/README.md);
the outputs that support a thesis claim are archived in `../tfm/docs/TFM/resultados/sondas/`, since
`logs/` is not versioned.

**Consolidated thesis sections** (`../tfm/docs/TFM/<section>.md`): `plataforma` (hardware and methodology), `procedencia_kernels` (origin of every
kernel), `tma`, `fp8`, `sparsity`, `pico_mma` (real tensor-core peak and the kernels as a
% of it) and `productividad` (code size and tuning cost vs performance per DSL).
**Energy efficiency** (`../tfm/docs/TFM/resultados/energia.md` + `figuras/energia_*`) is regenerated
after each `TFM_ENERGIA=1` run, or by hand with `python3.11 benchmarks/energia.py`. `../tfm/docs/TFM/resumen.md` summarizes the matmul study and `../tfm/docs/TFM/bitacora.md` is the
dated work log, with the Slurm jobs behind each claim.
